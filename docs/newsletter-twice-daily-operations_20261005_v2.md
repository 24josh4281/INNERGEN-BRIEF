# 뉴스레터 09:00·21:00 기준 운영 v2 (2026-10-05)

모든 시각은 Asia/Seoul 기준이다. 09:00과 21:00은 **기사 발행 시각의 제외 경계**다. 예약 시작, 실제 수집 완료, SMTP 접수, 수신함 도착은 각각 따로 기록한다. PC와 Codex 앱이 꺼지면 예약 실행은 보장되지 않는다. [v1](newsletter-twice-daily-operations_20261005_v1.md)은 저녁 발송 도구가 없던 이전 운영안으로 보존한다.

## 단일 소유 예약 두 개

| 기준 | 수집·생성 | 회사 메일 |
| --- | --- | --- |
| 매일 09:00 | 당일 09:00 미만 발행의 허용된 후보 수집, 원문·권리 검토, 오전 브리프와 6분야 후보 정리 | 기존 두 오전 메일의 준비·승인·중복 점검이 각각 통과할 때만 각 1회 접수 시도 |
| 매일 21:00 | 당일 09:00 이상~21:00 미만 발행 후보 수집, 출처·날짜 확인, 메타데이터 초안. 월요일에는 직전 완료 주의 주간 검토본 준비 | 6분야·고객사 **후보 메일**을 같은 회사 주소에서 같은 주소로 최대 1회 접수 시도. 원문 검증을 마친 4불릿 고객 브리프로 표시하지 않음 |

오전·저녁 수집은 서로 다른 run ID와 기준 시각을 쓴다. 저녁은 `tools/news_collector.py`에 당일 09:00 시작·21:00 종료를 시간대와 함께 지정한다. 같은 판본의 유효한 live run과 잠금을 먼저 확인한다. `run_report.json`, `articles.json`, `review_dates.json`, `collection_complete.json`의 시각과 SHA-256을 대조한다. `tools/build_daily_issue.py --run-dir <오늘 저녁 실행>`으로 메타데이터 검토본을 만들고, `tools/build_evening_curated_mail_digest.py`로 별도 메일 준비 파일을 만든다. 메일은 `tools/daum_smtp_mail.py dry-run --pointer output/mail_digest/latest_evening_curated.json`이 통과한 뒤에만 같은 `--pointer`로 `send`를 한 번 실행한다. 오전 `latest_curated.json`을 저녁 발송에 사용하지 않는다.

## 재시도·문제 해결

1. 오류를 발견하면 기준 시각, 기존 실행, 잠금, 소스별 오류, 원본 해시, 권리 상태를 먼저 확인하고 실패한 단계만 복구한다.
2. 허용된 일시 장애는 최초 시도 후 15분·30분에 재시도하고, 계속 같은 장애이고 안전할 때 45분에 세 번째 재시도한다. 총 재시도는 2~3회다. 매번 실제 시각과 결과를 기록한다. 성공한 수집·메일 단계는 다시 실행하지 않는다.
3. 권리·승인·robots·로그인·유료벽·CAPTCHA·API 키 부재는 반복 요청하지 않는다. KRX API는 하루 한 번만 실행한다. 허용된 대안이 없으면 원인과 필요한 조치를 알린다.
4. SMTP 접수 여부가 불명확하면 자동 재발송하지 않는다. 접수 장부와 시도 기록을 확인한다. 수치·배출량·가격을 추정하거나 바꾸지 않는다.
5. 복구 완료나 사용자 조치가 필요한 즉시 기준 시각, 시도 횟수·시각, 진단, 실제 해결 내용, 남은 조치와 기록 경로를 알린다. `BLOCKED`·`ERROR` 한 줄로 끝내지 않는다.

## 검증

- 발행 시각이 불명확한 기사는 기준 이전 발행을 입증할 수 없으므로 보류한다. 과거 실행과 다음 판본 기사를 섞지 않는다.
- 수집, 원문 검증, 배포권, 메일 승인, SMTP 접수, 수신함 도착을 서로 다른 상태로 남긴다.
- 같은 날짜·판본의 이미 완료된 작업은 건너뛰고, 수정본은 새 버전으로 보존한다.
- K-ETS Evaluator의 4불릿 고객 브리프 발송 도구는 09:00 기준만 검증한다. 저녁 21:00 메일은 기사 제목·매체·원문 링크의 후보 알림이다.
