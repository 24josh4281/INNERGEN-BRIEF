# 뉴스레터 09:00·21:00 기준 운영안 (2026-10-05)

모든 시각은 Asia/Seoul 기준이다. 09:00과 21:00은 **기사 발행 시각의 제외 경계**다. 예약 시작 시각, 실제 수집 완료, 메일 SMTP 접수, 수신함 도착은 서로 다른 사건으로 기록한다. PC 전원이 꺼지거나 Codex 앱이 실행되지 않으면 예약 시각을 보장할 수 없다.

## 예약 소유자

| 기준 | 단일 예약의 작업 | 외부 전달 |
| --- | --- | --- |
| 매일 09:00 | Carbon Issue Tracker의 허용된 뉴스 메타데이터 수집, 후보 목록, 시트·대시보드 점검, K-ETS Evaluator의 원문·권리 검토와 일간 브리프 준비 | 두 기존 회사 메일은 각각의 승인·중복 발송 점검을 통과할 때만 1회 접수 시도 |
| 매일 21:00 | 09:00 이상~21:00 미만 새 기사 후보 수집, 출처·날짜 확인, 내부 저녁 검토본 생성. 월요일은 주간 뉴스레터 검토본도 준비 | 현재 21:00 기준을 검증하는 메일 발송 경로가 없으므로 자동 외부 발송 없음 |

09:00·21:00판을 서로 다른 run ID와 기준 시각으로 관리한다. 수집은 수집 원장에, 검토 결과는 버전별 파일에 남긴다. `latest.json`만으로 판본을 판정하지 않는다. 수집 성공만으로 원문 검증이나 고객 배포권이 확보된 것으로 취급하지 않는다. 저녁 후보의 개별 원문을 검토하지 못하면 사실 서술형 뉴스레터라고 표시하지 않는다.

## 장애 복구와 알림

1. 오류가 나면 같은 기준 시각의 실행 여부, 잠금, 로그, 원본 파일·해시, 소스별 오류와 권리 설정을 먼저 확인한다. 병렬 수집이나 중복 산출물을 만들지 않는다.
2. 네트워크 일시 장애나 일시적인 파일 잠금 등 **허용된 일시 장애**에는 최초 시도 뒤 15분, 30분에 재시도한다. 계속 같은 장애이고 재시도가 안전하면 45분에 세 번째 재시도한다. 총 재시도는 2~3회다. 매번 성공·부분성공·실패와 실제 시각을 기록한다. 재실행 전에 이미 성공한 단계는 건너뛴다.
3. `BLOCKED`가 권리·API 승인·로봇 거부·로그인·유료벽·캡차·필수 원문·승인 부재를 뜻하면 같은 네트워크 요청을 반복하지 않는다. 승인된 다른 입력이 있으면 그 범위에서만 복구한다. KRX API는 해당 날짜에 한 번만 실행하고, 공개 페이지 예외도 하루 한 번의 조건과 별도 출처 표기를 지킨다.
4. SMTP 접수 결과가 불명확하면 재발송하지 않는다. 로컬 기록과 공급자 상태를 확인한 뒤 필요한 사용자 조치를 알린다. 수치·배출량·가격은 복구 과정에서 추정하거나 고치지 않는다.
5. 복구가 끝나거나 사용자 조치가 필요해진 즉시 알린다. 알림에는 기준 시각, 실패 단계, 시도 횟수와 실제 시각, 진단 결과, 자동으로 고친 내용, 아직 필요한 조치, 관련 파일 경로를 적는다. 단순 `BLOCKED`나 `ERROR` 한 줄로 끝내지 않는다.

## 검증 기준

- 오전 수집은 당일 09:00 이전, 저녁 수집은 당일 09:00 이상~21:00 미만의 발행 시각만 사용한다. 날짜만 있는 당일 기사는 기준 이전 발행을 입증할 수 없으므로 보류한다.
- 후보 수집, 원문 검증, 배포권, 메일 승인, SMTP 접수, 수신함 도착을 각각 별도 상태로 기록한다.
- 수집·편집 결과는 새 버전으로 보존하고 같은 날짜·판본의 이미 완료된 단계는 재실행하지 않는다.
- K-ETS Evaluator의 오전 메일 도구는 09:00 기준만 허용한다. 저녁판을 발송하려면 21:00 기준 검증·승인·중복 방지 도구를 별도로 구현하고 검증해야 한다.
